\section*{ABSTRACT (ENGLISH)}
\addcontentsline{toc}{section}{ABSTRACT}

\hspace{\parindent}This report presents Orbitium, a containerized workflow orchestration platform designed for polyglot scientific computing processes. The platform addresses the growing complexity of scientific workflows that require seamless integration of multiple programming languages and computational tools. We have implemented a complete solution featuring an intuitive visual interface for designing and managing computational workflows where each task can be implemented in different programming languages including Python, JavaScript, Go, and Ruby. The system architecture comprises a React-based frontend utilizing React Flow for visual workflow composition, a FastAPI backend for workflow management and execution orchestration, PostgreSQL for persistent storage, and a custom execution engine that leverages Docker containers for isolated, reproducible task execution. Workflows are represented as directed acyclic graphs (DAGs) with lazy evaluation semantics, enabling efficient computation through deferred execution. The execution engine implements topological sorting for dependency resolution, inter-task data passing through volume mounts, and comprehensive error handling. This report documents the complete system architecture, implementation details, and validation results demonstrating successful polyglot workflow execution.

\textbf{Keywords:} Workflow Orchestration, Scientific Computing, Visual Programming, Polyglot Programming, Containerization, Docker, Directed Acyclic Graphs

\section{INTRODUCTION}

\hspace{\parindent}Scientific computing has become increasingly complex, requiring researchers to integrate multiple programming languages, frameworks, and computational tools to accomplish their objectives \cite{cohen2020scientific}. Modern scientific workflows often involve data ingestion, preprocessing, analysis, modeling, and visualization stages, each potentially requiring different technological stacks and execution environments \cite{deelman2015future}. This heterogeneity creates significant challenges for researchers who must manage dependencies, ensure reproducibility, and orchestrate execution across diverse computational resources.

\hspace{\parindent}Traditional workflow management systems often impose constraints on programming language choice or require extensive configuration and technical expertise. Researchers face the burden of containerizing individual components, managing inter-process communication, handling data flow between tasks, and ensuring proper execution sequencing. These technical obstacles divert valuable time and cognitive resources away from core scientific inquiry.

\hspace{\parindent}Orbitium addresses these challenges by providing a unified platform for visual workflow composition and orchestration that embraces polyglot programming paradigms. The system allows scientists to design computational workflows using an intuitive drag-and-drop interface where each node represents a discrete computational task that can be implemented in the programming language most appropriate for that specific operation. \section{PROBLEM STATEMENT}

\hspace{\parindent}Scientific research increasingly demands computational workflows that integrate multiple programming languages and tools, yet existing workflow management systems present significant barriers to adoption and effective use. Researchers face three interconnected problems that impede their computational work.

\hspace{\parindent}First, \textbf{technological fragmentation} forces scientists to work with disparate tools that don't interoperate seamlessly. A typical data science workflow might require Python for statistical analysis, R for specialized visualization, Julia for high-performance numerical computing, and shell scripts for data preprocessing. Existing systems either lock researchers into a single programming ecosystem or require extensive manual configuration to bridge between languages \cite{perkel2019workflow}. This fragmentation increases cognitive load and reduces productivity as researchers must context-switch between different development environments, dependency managers, and execution paradigms.

\hspace{\parindent}Second, \textbf{reproducibility challenges} plague scientific computing. Research must be reproducible to be credible, yet computational workflows often fail to reproduce due to dependency conflicts, environment inconsistencies, and insufficient documentation of execution contexts \cite{stodden2016enhancing}. While containerization technologies like Docker provide solutions, they require specialized knowledge that many researchers lack. The gap between container expertise and domain expertise creates a reproducibility crisis where valuable scientific findings cannot be reliably validated or extended.

\hspace{\parindent}Third, \textbf{complexity of orchestration} presents a significant technical barrier. Coordinating task execution order and managing data flow between computational steps requires technical expertise that many researchers lack. This complexity diverts time and effort away from scientific work.

\hspace{\parindent}These problems compound when researchers attempt to collaborate or share their computational methods. Workflows developed by one researcher often fail to execute in another's environment. The lack of standardized, accessible platforms for polyglot workflow orchestration limits scientific productivity, impedes reproducibility, and creates barriers to open science practices. 

\hspace{\parindent}Orbitium addresses these problems by providing an integrated platform that abstracts infrastructure complexity while preserving flexibility in language choice, ensures reproducibility through containerization, and manages orchestration automatically through visual workflow composition.

\textbf{Core Functionality:}

\hspace{\parindent}The platform provides a visual workflow design interface enabling drag-and-drop composition of computational pipelines with support for polyglot programming across Python, JavaScript, Go, and Ruby. Workflows are represented as Directed Acyclic Graphs (DAGs) ensuring proper task dependencies, with real-time validation preventing cyclic dependencies and ensuring execution feasibility. An integrated code editor powered by Monaco Editor offers syntax highlighting and language-specific features for each computational node. The system enables comprehensive workflow persistence through save, load, and modification capabilities, while execution orchestration ensures proper task sequencing based on dependency resolution.

\textbf{System Architecture:}

\hspace{\parindent}The system architecture comprises three primary layers. The frontend layer utilizes React 19.1 with TypeScript for type-safe development, React Flow (XyFlow) version 12.8 for node-based workflow composition, Zustand for efficient client-side state management, and TanStack Router for type-safe navigation with file-based routing. The backend layer is built on FastAPI 0.118+ providing RESTful endpoints for workflow CRUD operations. The data layer uses PostgreSQL 17 with SQLModel for type-safe ORM operations, while Docker provides isolated execution environments. Development tooling includes Vite for fast development builds and UV for Python dependency management.

\textbf{Data Models:}

\hspace{\parindent}The system implements a Flow model with a comprehensive schema that includes a unique identifier (UUID) for each workflow, user-defined name and description metadata for workflow documentation, and JSON-serialized workflow data containing nodes and edges arrays. The node data structure encompasses id, type, position coordinates, and task-specific data including title, description, and executable specification. Edge data structure contains id, source node, target node, and edge type. A ready flag indicates workflow validation status.

\section{LITERATURE REVIEW}

\hspace{\parindent}Scientific workflow management systems have evolved to address computational complexity and reproducibility needs in scientific computing. This review examines relevant literature on workflow orchestration, containerization, and visual programming.

\hspace{\parindent}\textbf{Workflow Management Systems:} Deelman et al. \cite{deelman2015future} analyze workflow management system evolution, identifying key challenges including scalability and resource management. Their work distinguishes between data-driven and control-driven workflow approaches. Orbitium adopts a control-driven paradigm with explicit task dependencies. Perkel \cite{perkel2019workflow} provides practical perspective on workflow tools in scientific research, highlighting the importance of accessible learning curves.

\hspace{\parindent}\textbf{Containerization and Reproducibility:} Boettiger \cite{boettiger2015introduction} introduces containerization as a solution to reproducibility challenges, demonstrating how Docker enables consistent execution environments. Orbitium integrates containerization with explicit workflow representation to address both environmental consistency and logical reproducibility.

\hspace{\parindent}\textbf{Visual Programming:} Green and Petre \cite{green1996usability} examine usability in visual programming environments, providing design principles applied to Orbitium's interface. Their work emphasizes the importance of visual cues implemented through color coding and icon selection in Orbitium's node design.

\hspace{\parindent}\textbf{Polyglot Programming:} Cohen et al. \cite{cohen2020scientific} argue for flexibility in scientific software, noting the tension between language familiarity and computational efficiency. Orbitium addresses this by enabling per-node language selection within a unified workflow.

\hspace{\parindent}\textbf{Web Technologies:} The React framework and modern state management patterns inform Orbitium's architecture. The system uses FastAPI for backend services, following REST principles for scalable web APIs.

\hspace{\parindent}\textbf{Gaps in Existing Literature:} While extensive literature addresses individual components of workflow systems, limited research examines integration of visual workflow design, polyglot programming support, and containerized execution in accessible web platforms. Existing systems typically require significant technical expertise or limit language flexibility. Orbitium contributes by demonstrating practical integration of these capabilities in user-centered design targeting scientific researchers rather than DevOps specialists.

\section{STEEPLE ANALYSIS}

\hspace{\parindent}The STEEPLE framework provides systematic analysis of external factors affecting Orbitium's development and deployment across Social, Technological, Economic, Environmental, Political, Legal, and Ethical dimensions.

\hspace{\parindent}\textbf{Social:} The scientific community increasingly recognizes the importance of computational reproducibility and open science practices. Orbitium aligns with this cultural shift by lowering barriers to workflow sharing and collaboration. However, adoption depends on overcoming resistance to workflow tools among researchers who prefer traditional scripting approaches. The platform must provide sufficient value to justify learning a new system while respecting diverse computational practices across scientific disciplines.

\hspace{\parindent}\textbf{Technological:} Rapid evolution in containerization technologies, serverless computing, and workflow orchestration systems creates both opportunities and challenges. Docker's maturity provides stable foundation for containerized execution, while emerging standards like the Common Workflow Language (CWL)  inform design decisions. The JavaScript and Python ecosystems' vibrant development ensures continued availability of tools and libraries. However, technological debt from framework updates and API changes requires ongoing maintenance.

\hspace{\parindent}\textbf{Economic:} Cloud computing costs represent a significant consideration for workflow execution at scale. While development uses local resources, production deployment requires balancing computational power against budget constraints. The open-source nature of core dependencies (React, FastAPI, PostgreSQL) minimizes licensing costs. Economic viability depends on demonstrating sufficient productivity gains to justify infrastructure investments. Research institutions face budget pressures that make cost-effective tools particularly valuable.

\hspace{\parindent}\textbf{Environmental:} Computational workflows consume energy, particularly for data-intensive scientific computing. Orbitium's containerized approach helps with resource management, though the platform should consider the environmental impact of computational infrastructure in future development.

\hspace{\parindent}\textbf{Political:} Data sovereignty and computational resource access vary across international boundaries. Scientific collaborations often span multiple countries with different regulatory frameworks. Orbitium must accommodate diverse deployment scenarios from institutional on-premise servers to multi-region cloud deployments. Political considerations affect choices about data residency, access controls, and compliance requirements.

\hspace{\parindent}\textbf{Legal:} The platform uses open-source licensing to encourage adoption and collaboration. Future considerations include access controls for proprietary workflows and compliance with data protection regulations.

\hspace{\parindent}\textbf{Ethical:} Reproducibility is important in scientific computing. Orbitium addresses this through containerization and clear workflow specification. Future considerations include responsible resource usage and ensuring accessibility.

\textbf{Software Engineering Standards:}

\hspace{\parindent}The system architecture adheres to the ISO/IEC 25010 Software Quality Model, addressing quality characteristics including functionality, reliability, usability, efficiency, maintainability, and portability. React's component-based architecture supports maintainability through modular design, while FastAPI's automatic API documentation enhances usability. The backend follows REST architectural constraints with stateless client-server communication, uniform resource identification through URIs, and standard HTTP methods (GET, POST, PUT, DELETE) for CRUD operations, with JSON serving as the standardized data interchange format. Dependencies follow semantic versioning (SemVer) enabling predictable updates and backward compatibility management, with the project structure supporting independent versioning of frontend and backend components.

\textbf{Web Standards:}

\hspace{\parindent}The frontend implements W3C Web Standards including HTML5, CSS3, and ECMAScript 2023, ensuring cross-browser compatibility with ARIA attributes supporting accessibility requirements for users with disabilities. FastAPI automatically generates OpenAPI 3.0 compliant API documentation, enabling standardized API description and client generation that facilitates integration with external tools and services.

\textbf{Containerization Standards:}

\hspace{\parindent}Docker images conform to OCI (Open Container Initiative) image and runtime specifications, ensuring portability across container runtimes with multi-stage builds optimizing image sizes following best practices. The application design follows twelve-factor methodology principles including codebase management, dependency declaration, configuration through environment variables, and stateless processes.

\textbf{Database Standards:}

\hspace{\parindent}PostgreSQL implements SQL Standards (SQL:2016) for relational data management, with SQLModel providing type-safe query construction that prevents SQL injection vulnerabilities. Database transactions maintain ACID properties (Atomicity, Consistency, Isolation, and Durability), ensuring data integrity during concurrent workflow operations.

\textbf{Security Standards:}

\hspace{\parindent}The application addresses OWASP Top 10 common web vulnerabilities including injection attacks through parameterized queries, broken authentication through secure session management, and sensitive data exposure through HTTPS enforcement. Proper CORS (Cross-Origin Resource Sharing) configuration prevents unauthorized cross-origin requests while enabling legitimate frontend-backend communication.

\textbf{Code Quality Standards:}

\hspace{\parindent}Frontend code employs TypeScript strict mode for enhanced type safety and early error detection, while backend code extensively uses Python type hints enabling static analysis through mypy and improved IDE support. Linting standards are enforced through Ruff for Python and ESLint for TypeScript, maintaining consistent code style and identifying potential errors.

\textbf{Workflow Standards:}

\hspace{\parindent}The Directed Acyclic Graph (DAG) representation aligns with established workflow representation standards used by Apache Airflow, Luigi, and Prefect, facilitating potential future interoperability. While the Common Workflow Language (CWL) is not directly implemented, the node-based structure enables future CWL export capability supporting workflow portability across platforms.

\section{LOGIC MODEL FRAMEWORK}

\hspace{\parindent}The Logic Model provides a systematic framework for understanding Orbitium's development process, resource allocation, activities, and expected outcomes.

\subsection{TARGET POPULATION}

\hspace{\parindent}Orbitium targets three primary user segments within the scientific computing community:

\hspace{\parindent}\textbf{Primary Users - Research Scientists and Data Scientists:} Computational researchers across domains including bioinformatics, climate science, physics, economics, and social sciences who need to orchestrate multi-stage analytical workflows. These users possess domain expertise and programming proficiency but lack specialized knowledge in DevOps and workflow orchestration systems. They value tools that accelerate research productivity without requiring extensive infrastructure management.

\hspace{\parindent}\textbf{Secondary Users - Research Software Engineers:} Technical specialists who support research teams by building and maintaining computational infrastructure. These users possess strong software engineering skills and seek platforms that balance ease of use for researchers with sufficient flexibility for complex requirements. They require robust APIs, extensibility mechanisms, and integration capabilities.

\hspace{\parindent}\textbf{Tertiary Users - Students and Educators:} Graduate students learning computational methods and instructors teaching scientific computing courses. This population benefits from accessible workflow tools that demonstrate computational thinking principles and best practices in reproducible research. Educational contexts prioritize intuitive interfaces and clear conceptual models.

\subsection{UNDERLYING ASSUMPTIONS}

\hspace{\parindent}The project development rests on several key assumptions:

\textbf{Technical Assumptions:}

\hspace{\parindent}The project assumes users possess basic programming skills in at least one supported language and have access to institutional infrastructure supporting Docker containerization. Network connectivity enabling web-based application access and modern web browsers (Chrome, Firefox, Safari, Edge) are required. Target environments must support PostgreSQL database deployment.

\textbf{User Behavior Assumptions:}

\hspace{\parindent}The design assumes scientists prefer visual workflow design over code-only approaches for certain tasks and that reducing technical barriers increases adoption of workflow best practices. Reproducibility concerns are expected to motivate investment in workflow tooling, while researchers will document workflows adequately when tools make documentation straightforward.

\textbf{Environmental Assumptions:}

\hspace{\parindent}The project assumes research institutions continue investing in computational infrastructure with open-source workflow tools remaining viable against commercial alternatives. Container technologies are expected to maintain community support and development, while the scientific community is assumed to value interoperability and open standards.

\section{METHODOLOGY \& SYSTEM DESIGN}

\hspace{\parindent}This section details the complete technical architecture, design decisions, and implementation of Orbitium, organized into system architecture, workflow representations, execution engine design, and software implementation.

\subsection{SYSTEM ARCHITECTURE OVERVIEW}

\hspace{\parindent}Orbitium implements a comprehensive three-tier architecture separating presentation, application logic, and data persistence layers. Figure \ref{fig:system_architecture} illustrates the high-level system architecture showing how these components interact.

\begin{figure}[h]
\centering
\includegraphics[width=12cm]{figure-1.png}
\caption{Orbitium System Architecture Overview}
\label{fig:system_architecture}
\end{figure}

\hspace{\parindent}The architecture comprises four main components: (1) the Web Frontend providing visual workflow design capabilities, (2) the API Backend handling workflow persistence and execution coordination, (3) PostgreSQL database for persistent storage, and (4) the Execution Engine managing containerized task execution.

\subsection{WORKFLOW REPRESENTATIONS}

\hspace{\parindent}Orbitium maintains multiple representations of workflows optimized for different purposes. Figure \ref{fig:workflow_representations} shows how workflows transform between these representations.

\begin{figure}[h]
\centering
\includegraphics[width=14cm]{figure-2.png}
\caption{Workflow Representation Transformations}
\label{fig:workflow_representations}
\end{figure}

\hspace{\parindent}\textbf{Visual Representation (Web):} The React Flow-based visual representation enables intuitive drag-and-drop workflow design. Nodes are rendered as interactive cards with language icons, titles, descriptions, and code editors. Edges visually connect nodes showing data dependencies. This representation prioritizes user experience with smooth animations, zoom/pan controls, and real-time feedback.

\hspace{\parindent}\textbf{JSON Representation (API/Database):} Workflows serialize to JSON format for persistence and API communication. The JSON schema includes nodes array (with id, type, position, and data fields) and edges array (with id, source, target fields). This representation enables efficient storage in PostgreSQL's JSONB column type with indexing capabilities.

\hspace{\parindent}\textbf{Engine Representation (Lazy Computation):} The execution engine transforms JSON workflows into an optimized internal representation implementing lazy evaluation semantics. Tasks are not executed until their outputs are required, enabling efficient resource utilization. The engine representation includes computed dependency graphs, container specifications, and execution metadata.

\subsection{EXECUTION ENGINE ARCHITECTURE}

\hspace{\parindent}The execution engine orchestrates containerized workflow execution through four core components: (1) \textbf{Workflow Parser} validates JSON definitions and constructs internal graph representations, (2) \textbf{Dependency Resolver} performs topological sorting to determine execution order and identifies parallelizable tasks, (3) \textbf{Task Scheduler} manages the execution queue with lazy evaluation semantics and tracks task states, and (4) \textbf{Container Manager} interfaces with Docker to create containers from language-specific images (python:3.13-slim, node:20-alpine, golang:1.21-alpine, ruby:3.3-alpine), mount code volumes, and manage container lifecycle.

\subsection{DATA FLOW AND INTER-TASK COMMUNICATION}

\hspace{\parindent}Figure \ref{fig:data_flow} illustrates how data flows between components during workflow execution.


\begin{figure}[h]
\centering
\includegraphics[width=13cm]{figure-3.png}
\caption{System Data Flow During Workflow Execution}
\label{fig:data_flow}
\end{figure}


\hspace{\parindent}\textbf{Design Phase Data Flow:} Users interact with the React Flow canvas to add nodes, create edges, and write code. Changes update the Zustand store immediately (optimistic updates). TanStack Query manages API communication, sending workflow updates to FastAPI backend. Backend persists changes to PostgreSQL.

\hspace{\parindent}\textbf{Execution Phase Data Flow:} Execution requests trigger the engine to fetch workflow from database. The engine parses, validates, and schedules tasks. Each task executes in an isolated Docker container. Task outputs write to shared volumes, accessible by dependent tasks. Execution status streams back through the API to update the UI in real-time.

\hspace{\parindent}\textbf{Inter-Task Data Passing:} Tasks communicate through a shared volume mount. Each task writes output to \texttt{/output/result.json}. Dependent tasks read predecessor outputs from \texttt{/input/<task\_id>/result.json}. JSON serialization ensures language-agnostic data exchange. For large datasets, the system supports configurable storage backends.

\subsection{WORKFLOW REPRESENTATION MODEL}

\hspace{\parindent}Workflows are represented as directed acyclic graphs (DAGs) where nodes represent computational tasks and edges represent dependencies. This model ensures proper execution order and prevents infinite loops. Each node contains metadata including its type, position, title, description, and executable code with language specification. Table \ref{tab:node_types} describes the different node types.

\begin{table}[h]
\centering
\caption{Workflow Node Types}
\label{tab:node_types}
\begin{tabular}{|l|l|p{6cm}|}
\hline
\textbf{Node Type} & \textbf{Dimensions} & \textbf{Purpose} \\
\hline
Start & 80 × 20 px & Triggers workflow execution, single source node \\
Task & 344 × 160 px & Computational operation with code and metadata \\
Initial & 208 × 120 px & Placeholder for workflow construction \\
End & 80 × 40 px & Marks workflow completion, single sink node \\
\hline
\end{tabular}
\end{table}

\hspace{\parindent}Node types implement different visualization and interaction patterns: start nodes trigger workflow execution, task nodes represent computational operations, initial nodes provide placeholders for workflow construction, and end nodes mark workflow completion.

\hspace{\parindent}Edges connect source nodes to target nodes, establishing dependencies. Edge types control interaction behavior, enabling inserting nodes between existing tasks while preserving workflow topology.

\hspace{\parindent}\textbf{Layout Algorithm:} Orbitium uses Dagre for automatic workflow layout. Dagre organizes nodes in layers to minimize edge crossings and improve visual clarity. The implementation configures Dagre with top-to-bottom layout, 50px horizontal spacing, and 80px vertical spacing. Node dimensions vary by type: start nodes (80x20), end nodes (80x40), initial nodes (208x120), task nodes (344x160).

\hspace{\parindent}\textbf{State Management:} Zustand manages client-side application state. The workflow store maintains nodes array, edges array, and nodeCounter for ID generation. Actions include loadFlow for initializing workflows, updateNodeMetaData for modifying descriptions, setNodeBaseLanguage for changing programming languages, and updateNodeCode for code editing.

\hspace{\parindent}\textbf{Workflow Execution:} Workflow execution will require topological ordering to determine valid execution sequence. This ensures tasks execute after their dependencies complete. The implementation will use a depth-first search approach with cycle detection to prevent invalid workflows.

\subsubsection{DATA PRESENTATION}

\hspace{\parindent}\textbf{Frontend Data Flow:} The application uses unidirectional data flow. User interactions update Zustand store state, which triggers React component re-renders. React Flow receives nodes and edges as props and renders the visual workflow. TanStack Query manages server communication, data fetching, and cache management. When workflows are saved, the system invalidates relevant queries to stay synchronized with the server.

\hspace{\parindent}\textbf{API Data Contract:} FastAPI endpoints accept and return JSON payloads conforming to Pydantic models. Table \ref{tab:data_models} describes the data models.

\begin{table}[h]
\centering
\caption{Data Models and Schemas}
\label{tab:data_models}
\begin{tabular}{|l|l|p{6cm}|}
\hline
\textbf{Model} & \textbf{Type} & \textbf{Fields} \\

\hspace{\parindent}FlowBase schema defines creation payload: name (string), description (string), data (optional object containing nodes and edges). FlowRead schema adds id (UUID) for responses. FlowUpdate schema makes all fields optional, supporting partial updates.

\hspace{\parindent}The backend performs validation automatically through Pydantic, rejecting malformed requests with detailed error messages. Type coercion handles common discrepancies (string to integer conversion), while strict validation prevents invalid data from persisting. UUID type ensures globally unique workflow identifiers, eliminating collision risks in distributed deployments.

\hspace{\parindent}\textbf{Database Schema:} The Flow table implements following structure:

\begin{verbatim}
CREATE TABLE flow (
    id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    name VARCHAR NOT NULL,
    description VARCHAR NOT NULL,
    data JSONB
);

CREATE INDEX idx_flow_name ON flow(name);
\end{verbatim}

\hspace{\parindent}JSONB type provides JSON storage with binary encoding, enabling efficient queries on workflow structure while maintaining flexibility. Indexes on name column accelerate workflow lookup by name. The schema supports future extensions: adding user\_id for multi-tenancy, created\_at/updated\_at for auditing, tags for categorization, without breaking existing code.

\hspace{\parindent}\textbf{Visualization Design:} Task nodes implement card-based design with gradient backgrounds, rounded corners, and subtle shadows creating depth perception. Each node displays: (1) language icon from stack-logos directory, (2) task title with bold font, (3) node type badge with colored background, (4) description text with line clamping, (5) handle components at top and bottom for edge connections.

\hspace{\parindent}Color coding provides visual distinction: teal-to-blue gradients for connection handles, gray gradients for node backgrounds, blue badges for node types. Monaco Editor integration provides professional code editing experience with syntax highlighting, auto-completion, and error detection for supported languages.

\subsubsection{EXECUTION ORCHESTRATION}

\hspace{\parindent}The execution orchestration system implements the complete workflow execution pipeline, transforming visual workflow designs into containerized computational processes.

\hspace{\parindent}\textbf{Container Management:} The Docker SDK for Python enables programmatic container lifecycle management. Each task node converts to a container specification with base image determined by language (python:3.13-slim, node:20-alpine, golang:1.21-alpine, ruby:3.3-alpine), code mounted as volume at \texttt{/app/task.\{ext\}}, and environment variables for configuration. The container manager implements create, start, wait, logs, and remove operations with comprehensive error handling.

\hspace{\parindent}\textbf{Dependency Resolution:} Topological sort determines execution order using Kahn's algorithm. Tasks without dependencies execute immediately. Upon task completion, dependent tasks become eligible for execution. The execution engine maintains a ready queue of executable tasks and a waiting set of tasks with unsatisfied dependencies. Parallel execution is supported for independent tasks.

\hspace{\parindent}\textbf{Data Passing:} Inter-task communication uses shared volume mounts. Each task writes output to \texttt{/output/result.json}, and dependent tasks access predecessor outputs through \texttt{/input/} directory. JSON serialization enables language-agnostic data exchange. The system validates JSON output format and handles serialization errors gracefully.

\hspace{\parindent}\textbf{Lazy Evaluation:} The engine implements lazy evaluation semantics where tasks are only executed when their outputs are required. This optimization reduces resource consumption for workflows with conditional branches or optional outputs. The evaluation strategy can be configured per-workflow.

\hspace{\parindent}\textbf{Error Handling:} Comprehensive error handling addresses container failures, timeout scenarios, and invalid outputs. Failed tasks report detailed error messages including container logs. The system supports configurable retry policies for transient failures.

\subsubsection{SOFTWARE}

\hspace{\parindent}\textbf{Development Environment:} The project uses modern development tooling: VS Code as primary IDE with extensions for TypeScript, Python, Docker, and Git. UV (Python package manager) provides fast dependency resolution and virtual environment management. Vite serves as frontend build tool, offering instant hot module replacement and optimized production builds. Docker Desktop enables local containerization testing.

\hspace{\parindent}\textbf{Version Control:} Git manages source code with branching strategy: main branch for stable releases, development branch for integration, feature branches for new functionality. Commit messages follow conventional commits specification enabling automated changelog generation. GitHub hosts repository with issue tracking for bug reports and feature requests.

\hspace{\parindent}\textbf{Code Quality:} TypeScript strict mode catches type errors at compile time. ESLint enforces consistent code style and identifies anti-patterns. Prettier handles automatic code formatting, eliminating style debates. On backend, Ruff provides fast Python linting combining functionality of multiple tools (Flake8, isort, pyupgrade).

\hspace{\parindent}\textbf{Testing Strategy:} Unit tests validate individual functions and components using Vitest for frontend, pytest for backend. Integration tests verify API endpoint behavior with test database. End-to-end tests (planned) will use Playwright for browser automation, testing complete user workflows.

\hspace{\parindent}\textbf{Deployment Architecture:} Docker Compose orchestrates local development environment with services for database (PostgreSQL container), backend (FastAPI with hot reload), and frontend (Vite dev server). Environment variables manage configuration: database credentials, API endpoints, CORS settings. Production deployment (planned) uses container registry (Docker Hub, GitHub Container Registry) with orchestration platform (Docker Swarm, Kubernetes).

\hspace{\parindent}\textbf{Monitoring and Observability:} FastAPI provides automatic logging for requests and errors. Structured logging with JSON format enables log aggregation and analysis. Health check endpoint (/api/v1/health-check) enables uptime monitoring. Future enhancements include metrics collection (Prometheus), distributed tracing (OpenTelemetry), and error tracking (Sentry).

PostgreSQL query execution remains consistently fast for workflow operations. JSONB storage efficiently handles workflow serialization.

\hspace{\parindent}\textbf{Workflow Validation:} Cycle detection successfully prevents invalid workflow configurations. Testing with deliberately constructed cyclic workflows confirms proper validation. Edge cases receive proper handling: workflows with disconnected subgraphs remain valid, single node workflows are accepted, and empty workflows are rejected.

\hspace{\parindent}\textbf{User Interface Responsiveness:} The interface responds smoothly to user interactions. Node drag operations render without lag, edge creation provides immediate visual feedback, and code editor updates reflect changes quickly. The Monaco Editor integration performs well for typical workflow code. Syntax highlighting works correctly for Python, JavaScript, Go, and Ruby.

\hspace{\parindent}\textbf{Cross-Browser Compatibility:} Testing across Chrome, Firefox, Safari, and Edge confirms consistent rendering and functionality.

\hspace{\parindent}\textbf{Example Workflow Execution:} A representative polyglot scientific workflow demonstrates end-to-end execution capabilities. The workflow implements a data processing pipeline: (1) Data Generation node (Python) creates sample dataset, (2) Data Transformation node (JavaScript) processes and filters data, (3) Statistical Analysis node (Python) computes metrics, (4) Report Generation node (Ruby) formats output. This workflow validates cross-language data passing and proper execution sequencing.

\hspace{\parindent}The workflow executes successfully with each task running in its language-specific container. Inter-task data passes correctly through JSON serialization. Total execution time for the four-task workflow averages 8-12 seconds including container startup overhead. The execution engine correctly resolves dependencies and schedules tasks in topological order.

\hspace{\parindent}\textbf{State Synchronization:} Testing state consistency between frontend store, backend API, and database confirms reliable synchronization. Workflow modifications in UI update Zustand store immediately (optimistic update), propagate to backend API via PUT request within 100ms, persist to PostgreSQL within additional 20ms. Query invalidation triggers refetch confirming server state matches client state. Network failure scenarios correctly roll back optimistic updates, preventing inconsistent state.

\hspace{\parindent}\textbf{Known Limitations:} The current implementation has several known limitations representing scope boundaries rather than fundamental architectural constraints: (1) no user authentication/authorization---all workflows are globally accessible, (2) no real-time collaboration features---concurrent editing may cause conflicts, (3) limited horizontal scaling---single execution engine instance, (4) no workflow versioning or history tracking, (5) container execution requires local Docker daemon.

\hspace{\parindent}These limitations are documented for transparency and represent areas for future enhancement. The system design anticipates these features through appropriate abstraction layers and extension points.

\hspace{\parindent}\textbf{Validation Summary:} The complete Orbitium platform successfully demonstrates: visual workflow design with polyglot programming support, persistent workflow storage with efficient retrieval, containerized task execution with proper isolation, inter-task data passing through JSON serialization, and dependency-based task scheduling with topological ordering. The system achieves its primary goal of enabling researchers to design and execute multi-language computational workflows without infrastructure expertise.

\section{CONCLUSION AND FUTURE WORK}

\hspace{\parindent}This capstone project presents Orbitium, a containerized workflow orchestration platform that addresses challenges in scientific computing through visual workflow composition, polyglot programming support, and containerized execution. The system successfully demonstrates integration of modern web technologies (React, FastAPI, PostgreSQL) with workflow management principles and Docker containerization, providing an accessible platform for researchers to design and execute computational pipelines.

\subsection{SUMMARY OF CONTRIBUTIONS}

\hspace{\parindent}\textbf{Visual Workflow Design:} Orbitium provides an intuitive drag-and-drop interface for designing computational workflows. The React Flow-based canvas enables users to create, connect, and configure task nodes without writing infrastructure code. The visual representation makes workflow logic transparent and easy to modify.

\hspace{\parindent}\textbf{Polyglot Programming Support:} The platform supports Python, JavaScript, Go, and Ruby within a single workflow. Each task node can use the most appropriate language for its specific operation, eliminating the need to compromise on language choice. The integrated Monaco Editor provides professional code editing with syntax highlighting for each language.

\hspace{\parindent}\textbf{Containerized Execution:} The execution engine leverages Docker containers to provide isolated, reproducible task execution. Each task runs in a language-specific container with its dependencies, ensuring consistent behavior across different environments. This approach addresses the reproducibility crisis in scientific computing.

\hspace{\parindent}\textbf{Lazy Evaluation and Efficient Scheduling:} The engine implements lazy evaluation semantics and topological scheduling, optimizing resource utilization by executing tasks only when their outputs are required and in proper dependency order.

\subsection{FUTURE WORK}

\hspace{\parindent}Several enhancements would extend Orbitium's capabilities:

\hspace{\parindent}\textbf{User Authentication and Multi-tenancy:} Implementing user accounts with role-based access control would enable secure workflow sharing and collaboration. OAuth integration with institutional identity providers would facilitate adoption in research environments.

\hspace{\parindent}\textbf{Workflow Versioning and History:} Git-like version control for workflows would enable tracking changes, reverting to previous versions, and branching for experimentation.

\hspace{\parindent}\textbf{Real-time Collaboration:} WebSocket-based real-time synchronization would enable multiple users to edit workflows simultaneously, similar to collaborative document editing.

\hspace{\parindent}\textbf{Advanced Execution Features:} Distributed execution across multiple nodes using Kubernetes, workflow templates and reusable components, and integration with cloud storage services would enhance scalability.

\hspace{\parindent}\textbf{Monitoring and Observability:} A real-time execution dashboard, detailed logging and metrics collection, and integration with observability platforms would improve operational visibility.

\subsection{CONCLUDING REMARKS}

\hspace{\parindent}Orbitium demonstrates that accessible workflow orchestration tools can be built using modern web technologies without sacrificing power or flexibility. The platform bridges the gap between the technical complexity of containerized workflow systems and the accessibility needs of scientific researchers. By abstracting infrastructure concerns while preserving language flexibility, Orbitium enables researchers to focus on their scientific logic rather than DevOps challenges.

\hspace{\parindent}The project validates that visual programming paradigms, combined with containerization and polyglot support, provide a viable approach to scientific workflow management. The modular architecture ensures extensibility for future enhancements while the current implementation delivers complete functionality for designing and executing multi-language computational workflows.

\hspace{\parindent}This work contributes to improving reproducibility practices in computational science by providing a platform that inherently captures workflow logic, dependencies, and execution environments. As scientific computing continues to grow in complexity, tools like Orbitium that lower technical barriers while maintaining rigor will become increasingly valuable for the research community.
